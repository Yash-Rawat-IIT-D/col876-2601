# Extra Practice — Week of 10–16 Aug (Set 01)

**Aimed at:** the gaps you flagged — `Nat` and its `match` syntax, stating
theorems precisely, case analysis vs induction, induction over types you defined
yourself, and inductive predicates.

**How to use this file:** the four parts are a *chain*. Part B builds a number
type from nothing and Part C puts predicates on top of it; Part D generalises
what you learned there to arbitrary relations. Within a part, later questions
reuse earlier definitions verbatim, so keep them all in one file and do not
rename anything.

**Working rule for this whole set:** no `grind`, and no `omega` inside Parts B–D
(they would evaporate the exercise). `simp`, `rw`, `unfold`, `exact`, `apply` are
fine. Part A is where you may use the automation, deliberately, and compare.

## Part A — `Nat`, `match`, and case analysis (syntax drills)

### Q1. The two spellings of a successor [★]

**Define** the same function twice, once with each pattern syntax:

```lean
def pred1 : Nat → Nat        -- using  | 0 => .. | Nat.succ m => ..
def pred2 : Nat → Nat        -- using  | 0 => .. | m + 1 => ..
```

**Prove** `theorem pred_same : ∀ n : Nat, pred1 n = pred2 n`.

**Think about:** how many cases did the proof need, and why is it not one?
`pred1` and `pred2` are the *same* function after elaboration — so what exactly
is `rfl` unable to see when `n` is a variable?

### Q2. `match` inside a definition, three ways [★]

**Define** `sub2 : Nat → Nat` (subtract two, flooring at zero) in three styles:

```lean
def sub2a : Nat → Nat                        -- top-level pattern match, three cases
def sub2b (n : Nat) : Nat := match n with .. -- explicit `match ... with` in the body
def sub2c (n : Nat) : Nat := if n ≤ 1 then 0 else n - 2
```

`#eval` all three on `0, 1, 2, 7`. **Prove** `sub2a = sub2b` pointwise, and state
(you may `sorry`) the agreement with `sub2c`.

**Think about:** which of the three is easiest to `unfold` inside a proof? That
is a real design criterion when you define functions you intend to reason about.

### Q3. Case analysis as a theorem [★]

**Prove** the class's `allnat`, then sharpen it:

```lean
theorem allnat  : ∀ n : Nat, n = 0 ∨ (∃ m : Nat, n = m + 1)
theorem allnat2 : ∀ n : Nat, n = 0 ∨ n = 1 ∨ (∃ m : Nat, n = m + 2)
```

**Strategy:** `match n with` inside the tactic block (as in class), or `cases n`,
or `rcases`. Do `allnat2` with `match` on nested patterns `| 0 | 1 | k + 2` and
notice that this is exactly the shape of the `ev` definition from `aug_13.lean`.

### Q4. Predecessor laws [★]

**Prove**

```lean
theorem pred_succ : ∀ n : Nat, pred1 (n + 1) = n
theorem succ_pred : ∀ n : Nat, n ≠ 0 → pred1 n + 1 = n
```

**Think about:** the second needs a hypothesis, the first does not. Try stating
`succ_pred` without `n ≠ 0`, find the counterexample, and write it in a comment.
Then get the hypothesis *used*: after `cases n`, what discharges the zero case?
(`contradiction`, or `simp at h`, or `exact absurd rfl h` — try all three.)

### Q5. Three-way comparison [★★]

**Define**

```lean
def cmp : Nat → Nat → Ordering    -- .lt / .eq / .gt, by simultaneous recursion
```

**Prove**

```lean
theorem cmp_refl : ∀ n : Nat, cmp n n = Ordering.eq
theorem cmp_eq   : ∀ n m : Nat, cmp n m = Ordering.eq → n = m
```

**Strategy:** `cmp` recurses on both arguments, so `cmp_eq` needs an induction on
`n` that is general in `m` — after `induction n`, `intro m` *inside* the case, or
use `induction n generalizing m`. Getting this wrong is the single most common
beginner failure; do it wrong once on purpose and read the stuck goal.

### Q6. `Bool` and `Prop` are different worlds [★★]

**Prove**

```lean
theorem beq_to_eq : ∀ n m : Nat, (n == m) = true → n = m
theorem eq_to_beq : ∀ n m : Nat, n = m → (n == m) = true
theorem decide_eq : ∀ n m : Nat, decide (n = m) = (n == m)
```

**Think about:** write one sentence each on `n = m` (a `Prop`), `n == m` (a
`Bool`), and `decide (n = m)` (a `Bool` extracted from a `Decidable` instance).
Then explain why `if n = m then .. else ..` compiles at all for `Nat`.

### Q7. `Nat.le` is an inductive predicate you have already been using [★★]

`#print Nat.le`. It has exactly two constructors, `refl` and `step` — the same
shape as the `Le` you would define by hand.

**Prove**, by `cases` on the `≤` hypothesis (as in the class's `gezero`), *not* by
`omega`:

```lean
theorem ge_split : ∀ n m : Nat, n ≥ m → n = m ∨ n > m
theorem ge20     : ∀ n : Nat, n ≥ 20 → n = 20 ∨ n > 20
```

**Strategy:** `cases h with | refl => .. | step h' => ..`. In the `step` case you
will want `Nat.succ_le_succ`. Derive `ge20` from `ge_split` in one line.

### Q8. Same theorem, four tactics [★]

**Prove** `∀ a b : Nat, (a + b) * (a + b) = a * a + 2 * a * b + b * b` **four
times**, as `sq1 … sq4`:

1. by explicit `rw [...]` chains only (the class's route in `aug_10.lean`);
2. using `nth_rw` at least once;
3. by `simp` with the right lemma list;
4. by `grind`.

**Write a comment** ranking them by how much you learned vs how long they took.
This is the calibration exercise for the rest of the course: know which tool to
reach for, and know what it costs you to reach for the strong one first.

### Q9. Stating things precisely [★★]

Translate each English sentence into a Lean `theorem` statement (do not prove
them yet — precision is the exercise). Then decide, for each, whether it is true,
and prove or refute the ones you can.

1. "Every natural number is either even or odd, but not both."
2. "There is no largest natural number."
3. "Between any two distinct naturals there is a gap of at least one."
4. "If `n * m = 0` then `n = 0` or `m = 0`."
5. "Doubling is injective."

**Think about:** for (1) you need the predicates from `aug_13.lean`; for (2) the
∃ goes on the outside or the inside? Write both versions and say which one is
the sentence's real meaning.

## Part B — Build the natural numbers yourself

From here on, everything is your own type. This is the part that makes `induction`
stop feeling like magic: you will see the induction principle come directly from
the constructors you wrote.

### Q10. The type [★]

**Define**

```lean
inductive MyNat where
  | zero : MyNat
  | succ : MyNat → MyNat
  deriving Repr

namespace MyNat

def one : MyNat := succ zero
def two : MyNat := succ one
```

`#print MyNat.rec` and read the type of the recursor out loud. Identify, in a
comment, which argument is the base case and which is the inductive step, and
where the induction hypothesis sits.

### Q11. Addition [★]

**Define**

```lean
def add : MyNat → MyNat → MyNat     -- recurse on the FIRST argument
```

**Prove**

```lean
theorem add_zero_left  : ∀ n : MyNat, add zero n = n
theorem add_zero_right : ∀ n : MyNat, add n zero = n
```

**Think about:** one of these is `rfl` and the other needs `induction`. Say which,
and why, in one sentence. If you cannot say why, you do not yet understand what
your `def` compiled to.

### Q12. Addition is a commutative monoid [★★]

**Prove**, in this order (each uses the previous):

```lean
theorem add_succ  : ∀ n m : MyNat, add n (succ m) = succ (add n m)
theorem add_comm  : ∀ n m : MyNat, add n m = add m n
theorem add_assoc : ∀ n m k : MyNat, add (add n m) k = add n (add m k)
```

**Strategy:** no automation will save you here — there are no `Nat` lemmas to
borrow. Each proof is `induction` + `simp [add, ih]` or `rw`. When `rw` complains
that it cannot find the pattern, look at whether your goal has `add n (succ m)`
or `succ (add n m)`; those are different terms and only one matches.

### Q13. Multiplication [★★]

**Define** `def mul : MyNat → MyNat → MyNat` and **prove**

```lean
theorem mul_zero  : ∀ n : MyNat, mul n zero = zero
theorem mul_one   : ∀ n : MyNat, mul n one = n
theorem mul_succ  : ∀ n m : MyNat, mul n (succ m) = add (mul n m) n
theorem mul_comm  : ∀ n m : MyNat, mul n m = mul m n
theorem mul_add   : ∀ n m k : MyNat, mul n (add m k) = add (mul n m) (mul n k)
theorem mul_assoc : ∀ n m k : MyNat, mul (mul n m) k = mul n (mul m k)
```

**Strategy:** distributivity (`mul_add`) must come before associativity, and both
lean on `add_comm`/`add_assoc` for the rearrangements. If a proof stalls, the
missing step is almost always an `add` lemma you have not stated yet — state it
separately rather than fighting inside the big proof.

**Think about:** you have now rebuilt, by hand, what `omega` and `grind` give you
for free on `Nat`. Note down how many lemmas that took.

### Q14. Powers [★★]

**Define** `def pow : MyNat → MyNat → MyNat` (`pow b e` = b to the e) and prove

```lean
theorem pow_add : ∀ b n m : MyNat, pow b (add n m) = mul (pow b n) (pow b m)
```

### Q15. The bridge to `Nat` [★★]

**Define**

```lean
def toNat : MyNat → Nat
def ofNat : Nat → MyNat
```

**Prove**

```lean
theorem toNat_ofNat : ∀ n : Nat, toNat (ofNat n) = n
theorem ofNat_toNat : ∀ n : MyNat, ofNat (toNat n) = n
```

**Think about:** you have just proved the two types are isomorphic. Which
direction was easier, and why does the difficulty sit where it does?

### Q16. Transporting theorems across the bridge [★★★]

**Prove**

```lean
theorem toNat_add : ∀ n m : MyNat, toNat (add n m) = toNat n + toNat m
theorem toNat_mul : ∀ n m : MyNat, toNat (mul n m) = toNat n * toNat m
```

**Then**: re-prove `MyNat.add_comm` a *second* time, without induction on `MyNat`,
by pushing through `toNat`, using `Nat.add_comm`, and pulling back with Q15.

**Think about:** which proof of `add_comm` would you rather maintain? This
transport pattern (prove it once in the convenient model, transfer it) is exactly
what you will do when your verified checker's data structure differs from its
specification's.

### Q17. Subtraction is where it gets awkward [★★]

**Define** `def sub : MyNat → MyNat → MyNat` (truncated at `zero`) and **decide**
which of these are true. Prove the true ones; for each false one, give the
counterexample in a comment:

```lean
sub (add n m) m = n
add (sub n m) m = n
sub (sub n m) k = sub n (add m k)
```

**Think about:** this is a preview of why total functions with junk values make
statements have hypotheses. Compare with `head_def` on lists.

## Part C — Inductive predicates over your own type

### Q18. `≤`, two different ways [★★]

**Define both**:

```lean
inductive MyLe : MyNat → MyNat → Prop where
  | refl (n : MyNat)   : MyLe n n
  | step (n m : MyNat) : MyLe n m → MyLe n (succ m)

inductive MyLe2 : MyNat → MyNat → Prop where
  | zero (m : MyNat)     : MyLe2 zero m
  | succ (n m : MyNat)   : MyLe2 n m → MyLe2 (succ n) (succ m)
```

**Prove** each of these facts *twice*, once for each definition:

```lean
theorem le_zero      : ∀ n : MyNat, MyLe zero n
theorem le_succ_succ : ∀ n m : MyNat, MyLe n m → MyLe (succ n) (succ m)
```

**Think about:** for `MyLe`, the first is an induction and the second is work; for
`MyLe2` it is the reverse. Same relation, different *proof ergonomics*. Write two
sentences on when you would pick which — this is a real design decision you will
face when you define the transition relation for your project.

### Q19. The two definitions agree [★★★]

**Prove**

```lean
theorem le_iff : ∀ n m : MyNat, MyLe n m ↔ MyLe2 n m
```

**Strategy:** each direction is a rule induction that has to *rebuild* a
derivation in the other system, using the lemmas from Q18 as the bridge. If a
direction stalls, the missing piece is an inversion lemma
(`MyLe2 (succ n) (succ m) → MyLe2 n m`) — state it separately.

### Q20. Order properties [★★]

**Prove** (pick whichever definition makes each easier, and *say* which you
picked and why):

```lean
theorem le_trans    : ∀ n m k : MyNat, MyLe n m → MyLe m k → MyLe n k
theorem le_antisymm : ∀ n m : MyNat, MyLe n m → MyLe m n → n = m
theorem le_add      : ∀ n m : MyNat, MyLe n (add n m)
theorem le_mono_add : ∀ n m k : MyNat, MyLe n m → MyLe (add n k) (add m k)
```

### Q21. Strict order [★★]

**Define** `def MyLt (n m : MyNat) : Prop := MyLe (succ n) m` and **prove**

```lean
theorem lt_irrefl : ∀ n : MyNat, ¬ MyLt n n
theorem lt_trans  : ∀ n m k : MyNat, MyLt n m → MyLt m k → MyLt n k
theorem lt_or_ge  : ∀ n m : MyNat, MyLt n m ∨ MyLe m n
```

**Think about:** `MyLt` is a `def`, not an `inductive`. What can you no longer do
with it that you could do with an inductive predicate? (Hint: try `cases h` on a
`MyLt` hypothesis and see what happens — then try `unfold MyLt at h` first.)

### Q22. Evenness on `MyNat` [★★]

**Define**

```lean
inductive MyEv : MyNat → Prop where
  | zero    : MyEv zero
  | add_two : ∀ n : MyNat, MyEv n → MyEv (succ (succ n))
```

**Prove**

```lean
theorem myev_add    : ∀ n m : MyNat, MyEv n → MyEv m → MyEv (add n m)
theorem myev_double : ∀ n : MyNat, MyEv (add n n)
theorem myev_mul    : ∀ n m : MyNat, MyEv n → MyEv (mul n m)
theorem not_myev_one : ¬ MyEv one
```

**Strategy:** `myev_double` needs `add_succ` from Q12 to reshape the goal —
notice how a *definitional* lemma from Part B becomes the load-bearing step in a
*predicate* proof. That interplay is the point of this part.

### Q23. Divisibility by three [★★★]

**Define** `Div3 : MyNat → Prop` inductively (two rules) and **prove**

```lean
theorem div3_add : ∀ n m : MyNat, Div3 n → Div3 m → Div3 (add n m)
theorem div3_six : Div3 (add (add two two) two)
```

**Then** define a `Bool`-valued `div3b : MyNat → Bool` and **state** the
equivalence `∀ n, Div3 n ↔ div3b n = true`. Prove the easy direction; for the
hard one, recall the "carry three statements at once" trick from Practice 03 Q9 —
here it is three, not two. Explain why the number three appears.

### Q24. Inversion drills [★]

**Prove** each by `cases` (inversion), not induction:

```lean
theorem le_inv_succ  : ∀ n m : MyNat, MyLe (succ n) (succ m) → MyLe n m   -- (via MyLe2 if easier)
theorem ev_inv_two   : ∀ n : MyNat, MyEv (succ (succ n)) → MyEv n
theorem not_le_succ  : ∀ n : MyNat, ¬ MyLe (succ n) n
theorem zero_ne_succ : ∀ n : MyNat, zero ≠ succ n
```

**Think about:** the last one is not about a predicate at all — it is
constructor disjointness. Which tactic proves it, and what is the underlying
`MyNat.noConfusion` doing?

## Part D — Relations in general (and a first transition system)

This part generalises everything above: instead of a predicate on numbers, a
predicate on *pairs*, parameterised by an arbitrary relation. It is also the
first piece of machinery your semester project needs.

### Q25. Reflexive–transitive closure [★★]

**Define**

```lean
inductive Star {α : Type} (R : α → α → Prop) : α → α → Prop where
  | refl (a : α)         : Star R a a
  | step (a b c : α)     : R a b → Star R b c → Star R a c
```

**Prove**

```lean
theorem star_single : ∀ (α : Type) (R : α → α → Prop) (a b : α), R a b → Star R a b
theorem star_trans  : ∀ (α : Type) (R : α → α → Prop) (a b c : α),
                        Star R a b → Star R b c → Star R a c
```

**Strategy:** `star_trans` is a rule induction on the first derivation. Note how
the constructor `step` "cons"es a single step onto a chain — `Star` is literally a
list of steps, and the proof is literally `append`.

### Q26. The other associativity [★★★]

**Prove**

```lean
theorem star_step_right : ∀ (α : Type) (R : α → α → Prop) (a b c : α),
                            Star R a b → R b c → Star R a c
```

**Think about:** why is this *not* just `step` with the arguments swapped? Relate
your answer to `app_nil` vs `nil_app` in Practice 01 Q6 — it is the same
asymmetry, one level up.

### Q27. Monotonicity and idempotence [★★]

**Prove**

```lean
theorem star_mono : ∀ (α : Type) (R S : α → α → Prop),
                      (∀ a b, R a b → S a b) → ∀ a b, Star R a b → Star S a b
theorem star_star : ∀ (α : Type) (R : α → α → Prop) (a b : α),
                      Star (Star R) a b → Star R a b
```

### Q28. A concrete machine [★★]

**Define** a one-step relation on `Nat` and its reachability:

```lean
inductive Step : Nat → Nat → Prop where
  | double (n : Nat) : Step n (2 * n)
  | incr   (n : Nat) : Step n (n + 1)

def Reach (n m : Nat) : Prop := Star Step n m
```

**Prove**

```lean
theorem reach_two   : Reach 1 4          -- exhibit a derivation by hand
theorem reach_refl  : ∀ n : Nat, Reach n n
theorem reach_trans : ∀ n m k : Nat, Reach n m → Reach m k → Reach n k
```

**Think about:** `reach_two` has more than one proof (`1 → 2 → 4` by doubling
twice, or `1 → 2 → 3 → 4`). Write both. Proofs are objects; two proofs of the
same proposition are genuinely different terms.

### Q29. An invariant [★★★]

**Prove**

```lean
theorem reach_ge : ∀ n m : Nat, Reach n m → n ≥ 1 → m ≥ n
```

**Strategy:** rule induction on the `Star` derivation, with a `cases` on the
single `Step` inside each link. You will need the `n ≥ 1` hypothesis to survive
along the chain — check whether it does, and if not, strengthen the statement
until the induction closes. (This "find the invariant that is actually
inductive" step is the whole job in model checking.)

**Follow-up:** state and prove that every reachable number from `1` is `≥ 1`, and
then that `Reach 1 0` is false. Which of the two did the invariant give you?

### Q30. Predicates over structure, one last time [★★]

**Define** `Elem` for the `Tree α` type from Practice 01, as an inductive
predicate with three rules (here / left / right), and **prove**

```lean
theorem elem_mirror : ∀ (α : Type) (x : α) (t : Tree α), Elem x t → Elem x (mirror t)
theorem elem_flatten : ∀ (α : Type) (x : α) (t : Tree α), Elem x t → BelongsTo x (flatten t)
```

(`BelongsTo` and `flatten` are from Practice 04 and Practice 01.)

**Strategy:** the second needs the append lemmas for `BelongsTo` (Practice 04
Q3/Q4). This is the capstone: an inductive predicate over one datatype, a
recursive function into another, and a theorem tying them together — which is
the shape of every soundness proof you will write this semester.
