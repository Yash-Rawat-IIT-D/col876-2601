# Inductive Types and Induction

This note is about the Lean pattern behind data types, case analysis, recursive
functions, and induction proofs.

The central idea:

> An inductive type is a type generated by constructors.

Once you know the constructors, you know how to build values, how to inspect
values, and how to prove things about all values of that type.

---

## `inductive`

Use `inductive` to define a new type by listing its constructors.

```lean
inductive Day where
  | monday
  | tuesday
  | wednesday
  | thursday
  | friday
  | saturday
  | sunday
deriving Repr, DecidableEq
```

This creates a new type:

```lean
Day : Type
```

and seven constructors:

```lean
Day.monday : Day
Day.tuesday : Day
Day.wednesday : Day
```

and so on.

The constructor names live inside the `Day` namespace. If Lean already knows
the expected type is `Day`, you can often write:

```lean
.monday
```

instead of:

```lean
Day.monday
```

---

## `deriving`

`deriving` asks Lean to automatically generate useful standard behavior.

```lean
deriving Repr, DecidableEq
```

Common examples:

- `Repr`: lets Lean print values with `#eval`.
- `DecidableEq`: lets Lean decide equality between values of the type.

Example:

```lean
#eval Day.monday
#eval Day.monday == Day.tuesday
```

Without `Repr`, Lean may know the value exists but not know how to display it.

---

## Constructors

Constructors are the ways to build values of an inductive type.

For `Day`, every constructor is just a value:

```lean
Day.monday : Day
```

Some constructors can take arguments.

```lean
inductive MyNat where
  | zero : MyNat
  | succ : MyNat → MyNat
deriving Repr, DecidableEq
```

Here:

```lean
MyNat.zero : MyNat
MyNat.succ : MyNat → MyNat
```

So:

```lean
MyNat.succ MyNat.zero
```

is the custom natural number representing one.

This is the same shape as Lean's built-in `Nat`:

```lean
Nat.zero
Nat.succ Nat.zero
```

## `match`

Use `match` when you want to define something by cases.

```lean
def nextDay (d : Day) : Day :=
  match d with
  | .monday => .tuesday
  | .tuesday => .wednesday
  | .wednesday => .thursday
  | .thursday => .friday
  | .friday => .saturday
  | .saturday => .sunday
  | .sunday => .monday
```

The pattern:

```lean
match value with
| constructor_1 => result_1
| constructor_2 => result_2
```

Each branch says:

> if the value was built using this constructor, return this result.

Every branch must return the same type. In `nextDay`, every branch returns a
`Day`.

---

## Constructor Arguments in `match`

When a constructor carries data, the pattern gives you names for that data.

```lean
def isZero (n : MyNat) : Bool :=
  match n with
  | .zero => true
  | .succ _ => false
```

If you want to name the constructor argument, you could write:

```lean
| .succ k => false
```

Then Lean temporarily gives you:

```lean
k : MyNat
```

because `.succ` was built from a smaller `MyNat`.

This is the same "temporary box" feeling you saw with `Or.inl hp` and
`Or.inr hq`.

---

## Recursive Definitions

Recursive functions over inductive types usually follow the constructors.

```lean
def myAdd (n m : MyNat) : MyNat :=
  match n with
  | .zero => m
  | .succ k => .succ (myAdd k m)
```

The recursive call is on `k`, which is structurally smaller than `.succ k`.
Lean accepts this because it can see the recursion is moving toward `.zero`.

The same idea for lists:

```lean
def myLength {α : Type} (xs : List α) : Nat :=
  match xs with
  | [] => 0
  | _ :: rest => 1 + myLength rest
```

Lists have two basic shapes:

- `[]`: empty list
- `x :: xs`: head `x`, followed by tail `xs`

## `cases`

`cases` performs case analysis inside tactic mode.

```lean
theorem day_cases_example (d : Day) :
    d = .monday ∨ d ≠ .monday := by
  cases d with
  | monday =>
      left
      rfl
  | tuesday =>
      right
      intro h
      cases h
  | wednesday =>
      right
      intro h
      cases h
  | thursday =>
      right
      intro h
      cases h
  | friday =>
      right
      intro h
      cases h
  | saturday =>
      right
      intro h
      cases h
  | sunday =>
      right
      intro h
      cases h
```

The syntax pattern is:

```lean
cases value with
| constructor_1 =>
    proof_for_case_1
| constructor_2 args =>
    proof_for_case_2
```

`cases` gives one branch per constructor.

Use `cases` when you only need to split into cases, not use an induction
hypothesis.

## `induction`

Use `induction` when the type is recursive and you need a proof for all values.

For natural numbers:

```lean
theorem zero_add_custom (n : Nat) : 0 + n = n := by
  simp
```

That one does not need induction. But this direction does:

```lean
theorem add_zero_custom (n : Nat) : n + 0 = n := by
  induction n with
  | zero =>
      rfl
  | succ k ih =>
      change Nat.succ (k + 0) = Nat.succ k
      rw [ih]
```

The syntax pattern is:

```lean
induction n with
| zero =>
    proof_for_zero
| succ k ih =>
    proof_for_successor
```

In the successor case, Lean gives you:

```lean
k : Nat
ih : k + 0 = k
```

The `ih` is the induction hypothesis.

Natural deduction reading:

> To prove a statement for every natural number, prove it for `0`, then prove
> it for `k + 1` assuming it is already true for `k`.

---

## Induction on a Custom Type

For `MyNat`, induction follows the constructors you defined.

```lean
theorem myAdd_zero_right (n : MyNat) : myAdd n .zero = n := by
  induction n with
  | zero =>
      rfl
  | succ k ih =>
      change MyNat.succ (myAdd k .zero) = MyNat.succ k
      rw [ih]
```

The cases match the constructors:

```lean
MyNat.zero
MyNat.succ
```

So the induction proof has:

```lean
| zero => ...
| succ k ih => ...
```

The recursive constructor `.succ` gives both:

- `k : MyNat`
- `ih : myAdd k .zero = k`

## Induction on Lists

Lists are also inductive.

The constructors are:

```lean
List.nil
List.cons
```

The notation is:

```lean
[]
x :: xs
```

Example:

```lean
theorem append_nil_custom {α : Type} (xs : List α) : xs ++ [] = xs := by
  induction xs with
  | nil =>
      rfl
  | cons x rest ih =>
      change x :: (rest ++ []) = x :: rest
      rw [ih]
```

In the `cons` case, Lean gives you:

```lean
x : α
rest : List α
ih : rest ++ [] = rest
```

The goal is about:

```lean
x :: rest
```

So the induction hypothesis tells you the fact for the smaller list `rest`.

## `case`

Sometimes Lean names goals, and you can focus one goal using `case`.

This style:

```lean
theorem add_zero_custom_case (n : Nat) : n + 0 = n := by
  induction n
  case zero =>
    rfl
  case succ k ih =>
    change Nat.succ (k + 0) = Nat.succ k
    rw [ih]
```

is similar to:

```lean
theorem add_zero_custom_with (n : Nat) : n + 0 = n := by
  induction n with
  | zero =>
      rfl
  | succ k ih =>
      change Nat.succ (k + 0) = Nat.succ k
      rw [ih]
```

Use whichever style is clearer in the moment. I usually prefer `with` while
learning because it shows the constructor structure directly.

---

## Keyword Paradigm

The same small pattern appears everywhere:

| Task | Lean tool |
| --- | --- |
| define a type by constructors | `inductive` |
| build a value | use a constructor |
| compute by constructor shape | `match` |
| split a proof/data value into cases | `cases` |
| prove a theorem over recursive structure | `induction` |
| use the smaller recursive proof | induction hypothesis, often named `ih` |

When stuck, ask:

1. What type is this value?
2. What constructors can build values of that type?
3. Am I merely doing case analysis, or do I need an induction hypothesis?
4. In each branch, what temporary variables did Lean give me?
